How it works

intake → injection screen (ticket text is untrusted) → duplicate check (embedding similarity, in code) → one decision call: eleven typed questions (Choice / Score / Verify) answered as probability distributions by the engine behind the port (TypeSafe Jev, an LLM on a strict schema, or the offline rules) → composition in code (priority formula, routing matrix + overrides) → guardrails (completeness, distribution sanity, low-confidence forcing, safety flags) → agent gate. The model decides nothing consequential; code composes; the agent acts.

Policy impact replay (server-side, all stored runs)

The grown-up what-if: every stored run's recorded answers — decided runs included — are replayed through the real composition code under a hypothetical policy. No backend is called and nothing is saved; the report names the runs that would have landed differently.

Compare decision backends — one ticket, side by side

The same ticket is screened, decided and composed under each selected backend. Composition (priority, routing, guardrails) is the same code for every column — only the decision model differs. A comparison is an experiment: the ticket is not queued and nothing is gated. A backend that is not configured answers with an error column.

Conversation threads

Runs grouped at intake: same customer (normalised email, else name) + subject/body token containment over the policy threshold + inside 30 days. A thread is a label — grouping never merges or alters a run. A reopen joins its prior run's thread by construction. When the machine's grouping is wrong, an operator corrects it from a thread's detail below: attach, detach, merge — an audited overlay that never rewrites the computed grouping or any decision.

QA review — grade the triage, not the outcome

Calibration (Dashboards) scores the recorded probabilities against outcomes. This view grades the decisions: a seeded, stratified sample of decided runs — queue × priority band, in proportion — that a reviewer grades per family (category, priority drivers, routing, verify) plus overall. Confirmed duplicates never draw; runs already reviewed sit out unless you switch the exclusion off. Verdicts live on the review record: grading never edits a run, and the agreement report below tunes nothing — it is a read model for a human conversation. An optional overlap set assigns part of the draw to two named reviewers for double grading, so the report can also answer the second question: do the reviewers agree with each other?

Optional: name two reviewers and a run count, and that many of the drawn runs are assigned to both of them — only the pair may grade those runs, and the report measures whether the two agree with each other (Cohen's kappa per family).

Incident clustering — the outage is twenty tickets wearing twenty names

Threads group one customer's runs; this view groups many customers' runs around one underlying event. Proposals are computed in code on every load — same product area and category, arrivals inside the window of the group's first report, every member sharing enough of its words with that first report, at least the member floor — and the rule's constants print on the payload. A proposal is a view; confirming or dismissing it is the stored act, under a named lead. Membership lives on the incident record: it never edits, re-routes, re-prioritises or closes a member run — it badges the queue row, annotates the run's record view, and gives the lead one working list. A dismissed member set never proposes again; a set that gains a member may, and says which dismissal it outgrew.

Breach watch — the queue, ranked by the clock

Every run still waiting at the gate, ordered by the code SLA clock — each run against its own priority band's target — never by the model's sla_breach_risk judgement, which rides each row for the lead's eye and orders nothing. Bands are absolute distance to breach: breached, due within 1h (the critical band's whole target), due within 4h (the high band's), later. They are not the clock's own states — a low-band run is "due soon" in the clock's last-quarter sense with hours still left, and reads later here. The lead's one act is the reassignment: a named lead, a reason, and a new assignee, appended to the run's assignment trail. It moves the run between people — the clock, the composition and the status do not move, and nothing reassigns itself.

Shift handoff — one page, two signatures

At a shift change the outgoing lead composes one page from the desk's own views — the breach watch's counts and top rows, the open incidents and the proposals waiting on a lead, the per-queue SLA pressure, the QA review backlog — plus their own note, the only words on the page a human wrote. The figures are the source views' own, frozen at the stated boundary; nothing here recomputes them. The page stands outstanding until the lead it is addressed to accepts it — plainly, or with exceptions naming what they dispute. Exceptions ride beside the figures and edit none of them. The author cannot accept their own page, and a newer handoff supersedes an unaccepted older one, which stays on record as lapsed.

Template governance — a template earns its way live, and can lose the job

The template first-response draft is the only text this system composes toward a customer, and only for the safest slice. Its wording ships bundled — live at version 1 — until someone governs it. Authoring new words starts a record in draft: a draft never drafts. Promotion to live takes a named approver who is not the version's author, citing the basis. Editing a live template's words bumps its version and returns it to draft — the words never change silently under the approval that let them serve. The retirement watch reads the templates' own effectiveness figures: a live template whose reopen rate beats its category's baseline by more than the margin, over enough outcome-bearing uses, is proposed for retirement — and keeps serving until a named editor retires it, with a reason. Retired is terminal; the record and its history stay.
