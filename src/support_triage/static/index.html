How it works

intake → injection screen (ticket text is untrusted) → duplicate check (embedding similarity, in code) → one decision call: eleven typed questions (Choice / Score / Verify) answered as probability distributions by the engine behind the port (TypeSafe Jev, an LLM on a strict schema, or the offline rules) → composition in code (priority formula, routing matrix + overrides) → guardrails (completeness, distribution sanity, low-confidence forcing, safety flags) → agent gate. The model decides nothing consequential; code composes; the agent acts.

Policy — what the runs were composed under

Policy what-if (simulation)

Recomputes the currently open tickets in your browser under a hypothetical policy. Nothing is saved, sent, or changed on any record.

Policy impact replay (server-side, all stored runs)

The grown-up what-if: every stored run's recorded answers — decided runs included — are replayed through the real composition code under a hypothetical policy. No backend is called and nothing is saved; the report names the runs that would have landed differently.

Aggregates over every stored run — the same numbers as GET /api/stats/*.

Compare decision backends — one ticket, side by side

The same ticket is screened, decided and composed under each selected backend. Composition (priority, routing, guardrails) is the same code for every column — only the decision model differs. A comparison is an experiment: the ticket is not queued and nothing is gated. A backend that is not configured answers with an error column.

Conversation threads

Runs grouped at intake: same customer (normalised email, else name) + subject/body token containment over the policy threshold + inside 30 days. A thread is a label — grouping never merges or alters a run. A reopen joins its prior run's thread by construction.
